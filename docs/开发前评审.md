# Phase 1 开发前评审

> 评审版本：V1.0  
> 评审日期：2026-08-03  
> 评审范围：`PROJECT_RULES.md`、`docs/PRD.md`、`docs/技术方案.md`、`docs/开发计划.md`、`docs/Prompt设计.md`  
> 目标约束：个人开发者在 7 天内完成可演示 Demo  
> 评审结论：**有条件通过；完成本文“必须修改项”后再开始编码。**

## 1. 结论摘要

当前方案的产品方向、技术选型和阶段边界基本正确。以一名熟悉 React/TypeScript 的个人开发者、每天能够投入一个完整开发时段为前提，7 天完成本地可运行的 Phase 1 Demo 是可行的。

可行的核心原因是：Phase 1 已限定为单页、单接口、单次模型调用，不包含账号、数据库、文件上传、历史记录和后续求职功能。Next.js App Router 可以同时承载页面和服务端 API，适合小型全栈 Demo。

但目前尚不建议直接编码，原因不是功能太多，而是几个关键契约没有冻结：

1. AI 输出字段在 PRD、技术方案和 Prompt 之间仍有细微差异；
2. DeepSeek 请求参数、模型、非思考模式、JSON Output 和异常策略尚未确定；
3. “证据必须可校验”目前只有原则，没有可执行规则；
4. 测试方案和运行验收环境没有做最小化定义；
5. 部分非核心展示项会分散 7 天开发精力，应降为可延期项。

如果保持当前所有文档条目均为强制交付，7 天仍可能完成，但 Prompt 调试、异常处理和视觉打磨会相互挤压。建议进一步把 Phase 1 冻结为“一个输入区、一个服务端接口、六类结果、四类页面状态”。

## 2. 评审前提

### 2.1 时间前提

- 7 天指 7 个连续开发日，而不是零散业余时间；
- 开发者具备基本的 Next.js、React 和 TypeScript 使用经验；
- DeepSeek API 账号、有效 API Key、账户余额和网络连接在第 1 天前准备完成；
- 验收目标为本地可运行 Demo，不要求 7 天内完成生产部署和公开运营；
- 视觉目标为清晰、响应式、可演示，不要求品牌级动效或完整设计系统。

如果开发者是首次接触 Next.js 或每天只能投入 1–2 小时，7 天目标风险较高，应按 10–14 个日历日估算。

### 2.2 最终体验定义

Phase 1 验证的是：用户是否认可 AI 对一份 JD 的结构化解读。

本阶段不验证：

- 用户与岗位是否匹配；
- 岗位是否一定值得投递；
- HR 话术是否提高回复率；
- 面试回答是否提升录用率；
- 用户是否愿意长期保存求职资料。

## 3. 当前方案优势

### 3.1 产品范围已经明显收敛

- 主流程只有“输入 JD → 分析 → 展示结果”；
- 明确排除了账号、数据库、上传、抓取、自动投递和多模型等高成本功能；
- Phase 2–4 只作为路线存在，没有混入 Phase 1 实现；
- 用户价值能够在一次会话内被直接验证。

### 3.2 技术选型适合个人 Demo

- Next.js 同时承担页面和服务端 Route Handler，避免维护独立后端；
- TypeScript 可保证请求、模型结果和组件字段一致；
- Tailwind CSS 适合快速完成单页响应式界面；
- Zod 能在运行时拦截错误的模型输出；
- Phase 1 不使用数据库，显著降低开发、迁移和部署成本。

### 3.3 安全边界正确

- API Key 只在服务端环境变量中使用；
- 浏览器不直接调用 DeepSeek；
- JD 被定义为不可信文本；
- 模型原始输出需要通过 Schema 校验后才能展示；
- 日志不记录完整 JD；
- 项目规则明确禁止编造用户经历和输出绝对结论。

### 3.4 Prompt 已具备第一版基础

- 角色、受众和任务明确；
- 对硬性要求和加分项有清晰区分；
- 明确要求事实、推断和待确认信息分开；
- 包含提示注入防护；
- 要求输出 JSON，并限制部分数组数量；
- 已设计代表性回归样例类型。

## 4. 发现的问题

## 4.1 七天范围仍有少量非核心项

当前 PRD 同时要求岗位名、公司名、示例 JD、字数提示、术语解释、积极信号、完整复制和多类分析说明。这些功能单独看都不大，但会增加字段、布局、Prompt 和测试组合。

其中真正验证核心假设的内容只有：

- JD 输入；
- 岗位概述；
- 核心职责；
- 任职要求分类；
- 风险/注意事项；
- 待确认问题与信息缺口；
- 加载、失败和重试。

术语解释、积极信号、示例 JD、完整结果复制不应阻塞 Demo 验收。

## 4.2 文档间的输出契约不完全一致

主要问题：

- 技术方案只展示顶层空数组，没有定义每个数组元素的完整形状；
- Prompt 中 `coreCapabilities` 和 `niceToHave` 为空数组示例，无法据此建立严格 Schema；
- `type` 字段只在部分模块出现，无法稳定满足“事实/推断/待确认”区分；
- `fact|inference` 写成一个示例字符串，模型可能把它当成字面值，而不是枚举候选；
- PRD 要求“分析说明”，API 响应中没有统一字段承载；
- 技术方案声明存在 `EvidenceItem`，但 Prompt 输出没有统一证据对象；
- `confidence` 在技术方案中被描述为可选，Prompt 契约中又没有该字段。

如果直接开发，最可能出现的返工是：Zod Schema、TypeScript 类型、Prompt 示例和页面组件各自定义一版字段。

## 4.3 证据校验规则过于模糊

Prompt 文档提出 `evidence` 应能在 JD 中找到“或至少与原文高度一致”。后半句无法用简单程序稳定判断，也容易让模型改写证据。

对于 7 天 Demo，推荐将 `evidence` 定义为 JD 中的短原文引用，服务端使用标准化后的字符串包含检查。允许忽略首尾空白和连续空格差异，但不做语义相似度或向量检索。

若某项属于推断，也应引用触发该推断的原文；没有依据则不输出该项，改放入信息缺口。

## 4.4 DeepSeek 调用方案方向正确，但缺少可执行配置

当前“服务端调用 + JSON + Zod”是合理方案，但以下内容没有冻结：

- 具体模型；
- 思考或非思考模式；
- API 基础地址和接口；
- `response_format`；
- `max_tokens`；
- 温度；
- 请求超时；
- 空内容处理；
- `finish_reason` 非正常结束处理；
- 哪些 HTTP 错误可以重试；
- 是否采用原生 `fetch` 或兼容 SDK。

根据 2026-08-03 的 DeepSeek 官方文档，Chat Completions 支持 JSON Output；启用时需要同时设置 `response_format: {"type":"json_object"}`、在 Prompt 中明确要求 JSON，并设置合理的输出 token 上限。官方也明确提示 JSON Output 偶尔可能返回空内容，因此必须将空内容作为显式异常处理。[DeepSeek JSON Output](https://api-docs.deepseek.com/guides/json_mode/)

当前官方 Chat Completions API 的思考模式默认为启用。对 Phase 1 这种结构化抽取任务，默认思考会带来不必要的延迟和输出复杂度，应明确使用非思考模式。接口还会返回 `finish_reason`，包括 `stop`、`length`、`content_filter` 和资源不足等结果，服务端必须检查，而不能只读取文本。[DeepSeek Chat Completions API](https://api-docs.deepseek.com/api/create-chat-completion/)

官方错误码包含 400、401、402、422、429、500 和 503，需要映射为开发诊断与用户可理解提示。[DeepSeek Error Codes](https://api-docs.deepseek.com/quick_start/error_codes/)

## 4.5 模型名称存在时效性风险

DeepSeek 模型和计费会更新。当前官方文档列出 `deepseek-v4-flash` 与 `deepseek-v4-pro`，两者均支持 JSON Output；对成本和速度优先的个人 Demo，建议默认使用 Flash，并通过服务端环境变量配置模型名称，避免散落硬编码。[DeepSeek Models & Pricing](https://api-docs.deepseek.com/quick_start/pricing/)

模型选择属于易变化配置，不应成为页面或 Prompt 的固定业务逻辑。正式开发当天仍需再次核对官方文档。

## 4.6 前后端结构略有重复风险

技术方案同时规划 `lib/schemas.ts` 和 `types/analysis.ts`。若手写两套相同定义，后续容易漂移。

建议：

- 以 Zod Schema 为唯一运行时真相；
- TypeScript 类型从 Schema 推导；
- `types/analysis.ts` 仅在确有必要时重新导出推导类型，不重复手写字段；
- Route Handler、前端状态和结果组件共用同一类型定义。

页面方面无需全局状态库。建议保留一个客户端交互容器管理输入、加载、错误和结果；结果卡片保持无状态展示组件。`page.tsx` 只负责页面框架即可。

## 4.7 错误恢复缺少最低策略

“错误提示和重试”已经写入 PRD，但没有明确：

- 请求超时多少秒；
- 是自动重试还是仅用户手动重试；
- API 返回无效 JSON 时是否再次调用模型修复；
- 失败时页面是否保留上一次成功结果；
- API Key 错误和账户余额不足时应该如何提示开发者。

对于 Phase 1，推荐简单策略：单次请求设应用级超时；不做第二次模型修复；429、500、503 和空内容最多自动重试一次，其他错误不自动重试；所有失败均保留用户 JD 并允许手动重试。

## 4.8 测试范围缺少数量和通过门槛

当前测试“类型”足够，但没有说明最少样例数和通过标准。七天 Demo 不需要大型评测系统，但至少需要：

- 5–10 条固定 JD 回归样例；
- 1 条加分项密集 JD；
- 1 条信息不足 JD；
- 1 条提示注入 JD；
- 1 条非招聘文本；
- 请求 Schema 和响应 Schema 的自动测试；
- DeepSeek 错误响应的模拟测试。

AI 语义结果不应使用全文快照做严格相等测试，应检查结构完整性、枚举合法性、证据可追溯性和关键分类规则。

## 4.9 Demo 的验收环境没有明确

README 写明部署待定，PRD 又要求桌面端和手机浏览器可用。两者不冲突，但容易在第 7 天临时增加部署工作。

建议 Phase 1 的强制验收环境定义为：

- 本地运行；
- 桌面浏览器完成真实 API 调用；
- 使用浏览器移动端视口完成响应式验收；
- 公开部署为可延期项。

## 5. 必须修改项

以下内容应在正式编码前冻结并同步回 PRD、技术方案、Prompt 和开发计划。它们属于开发契约，不是新增功能。

### M1. 冻结 Phase 1 最终范围

将强制交付范围限定为：

1. 单页 JD 文本输入；
2. 输入校验；
3. 开始分析；
4. 加载、成功、失败、重试四类状态；
5. 单个服务端分析接口；
6. DeepSeek 单次结构化分析；
7. 六类结果展示；
8. 基础响应式布局；
9. 核心自动测试与固定样例；
10. 本地运行说明。

岗位名称、公司名称保留为非必填小字段，但不允许因此影响分析流程。

### M2. 建立唯一输出契约

建议最终仅保留以下数据：

| 字段 | 用途 | 元素最低字段 |
|---|---|---|
| `summary` | 一句话岗位概述 | 字符串 |
| `coreResponsibilities` | 3–6 项核心职责 | 标题、解释、原文证据、依据类型 |
| `requirements.mustHave` | 明确硬性要求 | 内容、原文证据、依据类型 |
| `requirements.coreCapabilities` | 核心能力 | 内容、解释、原文证据、依据类型 |
| `requirements.niceToHave` | 明确加分项 | 内容、原文证据、依据类型 |
| `riskSignals` | 需要谨慎确认的信号 | 内容、原因、原文证据、待确认标记 |
| `questionsToAsk` | 建议问 HR 的问题 | 问题、来源理由 |
| `unknowns` | 影响判断但 JD 未说明的信息 | 字符串 |

`依据类型` 使用真正的枚举值，例如“JD 明示”或“基于 JD 推断”，不得使用包含竖线的示例字符串。

Schema 完成后，PRD、Prompt 示例、Zod、TypeScript、API 响应和结果组件必须使用同一字段名。

### M3. 固定证据规则

- 证据必须是 JD 中的短原文引用；
- 服务端仅做标准化字符串包含校验；
- 没有证据的硬性要求不得通过校验；
- 推断必须有触发推断的原文，并明确标记为推断；
- 不在 Phase 1 引入向量检索、语义相似度或第二次模型核验。

### M4. 固定 DeepSeek 最小调用配置

开发前应在技术文档中明确：

- 使用官方 OpenAI 兼容的 Chat Completions 接口；
- 基础地址和模型均由服务端配置集中管理；
- 默认模型采用当前可用的 Flash 模型，模型名通过环境变量配置；
- 结构化抽取使用非思考模式；
- 使用 JSON Output；
- Prompt 中明确出现 JSON 要求并提供完整输出示例；
- 设置合理的 `max_tokens`，并处理 `finish_reason = length`；
- 使用较低温度以提高分类稳定性；
- 空内容、无 choices、无法解析、Schema 失败均视为 AI 输出错误；
- 使用应用级超时，不跟随供应商可能持续很久的连接等待；
- 明确 HTTP 错误码映射和最多一次的重试规则。

建议优先使用平台原生 `fetch`，减少额外 SDK 依赖。若选择 OpenAI 兼容 SDK，也必须由单独的 DeepSeek 适配模块封装，页面和 Route Handler 不直接依赖 SDK 返回结构。

### M5. 固定输入限制与隐私提示

开发前需要给出明确数值：

- JD 最小字符数；
- JD 最大字符数；
- 岗位名和公司名最大字符数；
- 用户界面提示不要粘贴手机号、邮箱、身份证等不必要个人信息。

推荐 Demo 初值：JD 100–12,000 个字符，岗位名和公司名各不超过 100 个字符。该数值属于工程保护值，后续可根据真实 JD 调整。

### M6. 固定错误和重试策略

- 400/422：请求配置或参数错误，不自动重试；
- 401：API Key 配置错误，不自动重试；
- 402：账户余额不足，不自动重试；
- 429/500/503：短暂等待后最多自动重试一次；
- 请求超时：停止当前请求，用户手动重试；
- JSON 空内容：最多自动重试一次；
- JSON 可解析但 Schema 不通过：不做昂贵的二次修复，返回可重试错误；
- 页面始终保留原始输入。

建议应用级超时先设为 60 秒，再根据实测调整。该值不得散落在多个文件中。

### M7. 固定测试最小集合

开发计划中加入以下完成定义：

- 请求 Schema 单元测试；
- 响应 Schema 单元测试；
- 证据包含校验测试；
- DeepSeek 成功、空内容、无效 JSON、429 和 500 的模拟测试；
- 页面成功、加载、错误和重试状态测试；
- 至少 5–10 条固定 JD 人工回归样例；
- `npm run lint`、测试和构建均通过后才算完成。

### M8. 明确验收环境

Phase 1 的必交结果定义为“本地可运行 Demo”。公开部署、域名、监控和在线限流不作为 7 天阻塞项；如果第 7 天前核心功能稳定，可作为额外交付。

## 6. 可以延期项

以下内容不会影响核心假设验证，可延期到 Phase 1.1 或在 7 天有余量时完成：

| 项目 | 延期原因 |
|---|---|
| 示例 JD 一键填充 | 便利性功能，不影响主流程 |
| 字数实时计数 | 校验必须保留，实时计数可延期 |
| 复制完整分析结果 | 展示是核心，复制不是 |
| 术语解释模块 | 会增加 Prompt 长度、Schema 和卡片数量 |
| 积极信号模块 | 定义较主观，易与岗位概述重复 |
| 复杂置信度评分 | 容易造成伪精确，第一版不需要 |
| 多次自动修复 AI 输出 | 增加成本和异常分支 |
| 流式输出 | 结构化 JSON 需要完整结果后校验 |
| 公开部署 | 本地 Demo 已能验证核心闭环 |
| 埋点、监控平台 | 单人本地 Demo 可先使用最小诊断日志 |
| UI 动效和完整设计系统 | 不影响产品价值验证 |
| 保存历史分析 | 需要持久化设计，明确不属于 Phase 1 |

## 7. Phase 1 最终开发范围

### 7.1 必须完成

#### 输入区

- 一个 JD 多行文本框；
- 可选岗位名称；
- 可选公司名称；
- 最小/最大长度校验；
- “开始分析”按钮；
- 请求期间禁止重复提交。

#### 服务端

- 一个 `POST /api/analyze` Route Handler；
- 请求体 Schema 校验；
- 服务端读取 DeepSeek 环境变量；
- DeepSeek Chat Completions 非思考模式调用；
- JSON Output；
- 超时、错误码和一次性重试策略；
- 响应 JSON 解析、Zod Schema 和证据校验；
- 统一成功与错误响应。

#### 分析结果

1. 岗位一句话概述；
2. 核心职责；
3. 硬性要求；
4. 核心能力与加分项；
5. 风险/注意事项；
6. 建议向 HR 确认的问题与信息缺口。

#### 页面状态

- 初始状态；
- 加载状态；
- 成功状态；
- 错误状态和重试。

#### 质量

- 基础响应式布局；
- 核心 Schema 和接口模拟测试；
- 固定 JD 回归样例；
- 本地启动说明；
- 文档与更新日志同步。

### 7.2 明确不做

- 用户账号；
- 数据库；
- 历史记录；
- 文件上传和 OCR；
- URL 抓取；
- 个人经历；
- 匹配分析；
- 投递推荐等级；
- HR 沟通话术；
- 面试准备；
- 自动投递；
- 流式生成；
- 多模型切换；
- 后台管理；
- 付费；
- 生产级可观测系统。

## 8. 推荐前后端结构

不需要改变 Next.js 单体方向，只需减少重复定义。

```text
Next.js 页面框架
└── 客户端分析容器
    ├── JD 输入表单
    ├── 状态管理
    └── 分析结果展示

Route Handler
├── 请求 Schema
├── DeepSeek 适配器
├── Prompt 模板
├── 响应 Schema
├── 证据校验
└── 错误映射
```

结构原则：

- 不引入 Redux、Zustand 等全局状态库；
- 不引入独立后端；
- 不重复手写 TypeScript 类型和 Zod Schema；
- DeepSeek 供应商细节只存在于适配器；
- Prompt 文本与 Schema 版本集中管理；
- 结果组件不负责发请求或解析模型文本。

## 9. Prompt 第一版可行性

### 9.1 结论

当前 Prompt 的角色、边界和安全规则能够支持第一版，但输出契约尚不能直接用于开发。完成 M2、M3 和 M4 后即可使用，无需增加多阶段 Prompt、工具调用或链式工作流。

### 9.2 第一版应保留

- 面向应届生和 0–1 年经验用户；
- 只分析 JD；
- JSON 输出；
- 不补造信息；
- 区分硬性要求和加分项；
- 风险使用审慎措辞；
- 重要结论带原文证据；
- 忽略 JD 内嵌指令；
- 数组数量限制；
- 信息不足时输出未知项。

### 9.3 第一版应简化

- 移除非核心的积极信号和术语解释，或设为可选扩展；
- 不输出数字置信度；
- 不要求模型给出投递结论；
- 不做个人经历或匹配分析；
- 不让模型自行决定字段结构；
- 不做第二次模型自我反思或格式修复。

### 9.4 Prompt 最低质量门槛

- 合法 JSON；
- 通过统一 Schema；
- 加分项不进入硬性要求；
- 硬性要求均有原文证据；
- 推断明确标记；
- 缺失信息不被补造；
- 提示注入样例不改变输出格式或任务。

## 10. 开发前必须补充的内容

在开始编码前，应先由项目方确认或准备：

1. DeepSeek API Key 已创建且账户可正常调用；
2. API 账户有可用余额；
3. 确认第一版使用当前 Flash 模型并采用非思考模式；
4. 确认 Demo 只要求本地运行，不要求公开 URL；
5. 确认本文精简后的六类输出为最终强制范围；
6. 选择 Node.js 版本和包管理器，并在项目中锁定；
7. 选择最小测试方案；
8. 准备 5–10 条允许用于开发测试的脱敏 JD；
9. 将本文 M1–M8 同步回相关正式文档；
10. 建立 `.env.example` 的变量名称说明，但不得写入真实密钥。

其中 1–5 属于开工条件；6–10 可在第 1 个开发日完成。

## 11. 推荐开发顺序

### 第 1 天：冻结契约并初始化项目

- 确认最终范围；
- 同步 PRD、技术方案和 Prompt；
- 初始化 Next.js、TypeScript、Tailwind；
- 锁定 Node.js、包管理器和环境变量名称；
- 建立请求 Schema、响应 Schema 和共享类型。

完成标准：应用可启动，Schema 与文档完全一致。

### 第 2 天：打通 DeepSeek 服务端调用

- 建立 DeepSeek 适配器；
- 完成 Prompt 模板；
- 实现非思考 JSON Output 请求；
- 处理正常响应、空内容、超时和错误码；
- 使用一条真实脱敏 JD 完成端到端调用。

完成标准：服务端能够稳定返回通过 Schema 的结构化结果。

### 第 3 天：完成核心页面流程

- 完成 JD 输入表单；
- 接入 `/api/analyze`；
- 完成初始、加载、成功和错误状态；
- 保留失败输入并支持重试。

完成标准：用户可独立完成一次分析。

### 第 4 天：完成结果展示

- 展示六类核心结果；
- 展示证据和事实/推断标签；
- 处理空数组和信息不足；
- 完成基础响应式布局。

完成标准：桌面和移动视口均可清楚阅读。

### 第 5 天：Prompt 调试与固定样例

- 使用 5–10 条固定 JD 回归；
- 修正硬门槛和加分项分类；
- 检查风险措辞、证据和未知信息；
- 固定 Prompt 版本。

完成标准：关键质量门槛通过，Prompt 不再随 UI 开发频繁改变。

### 第 6 天：测试与异常处理

- 完成 Schema、证据和错误映射测试；
- 模拟空内容、无效 JSON、429 和 500；
- 检查重复提交、超时和手动重试；
- 执行 lint、测试和构建。

完成标准：核心失败路径可恢复，检查全部通过。

### 第 7 天：验收、修复和文档

- 按 PRD 逐项验收；
- 修复阻断问题；
- 更新 README 和更新日志；
- 整理演示 JD 和演示步骤；
- 如有余量，再完成延期项。

完成标准：本地 Demo 可重复演示，不依赖临时手工修改。

## 12. 七天风险与应对

| 风险 | 概率 | 影响 | 应对 |
|---|---|---|---|

| DeepSeek 延迟过长 | 中 | 中 | Flash、非思考模式、应用级超时 |

| UI 打磨挤压测试时间 | 中 | 中 | 只做清晰的基础样式，动效延期 |
| 证据引用无法自动校验 | 中 | 中 | 使用短原文和字符串包含检查 |
| 临时加入 Phase 2 功能 | 中 | 高 | 按 `PROJECT_RULES.md` 拒绝范围扩张 |

## 13. 最终评审意见

Phase 1 **符合个人开发者 7 天完成 Demo 的目标**，但前提是：

1. 将术语解释、积极信号、复制和公开部署降为可延期项；
2. 开发前统一 AI 输出 Schema 和证据规则；
3. 明确 DeepSeek 的 Flash、非思考、JSON Output、超时与错误策略；
4. 只做本地单页 Demo，不引入持久化和后续 Phase；
5. 将 Prompt 调试纳入开发排期，而不是视为接口接通后的附带工作。

本次评审不建议更换技术栈，也不建议拆分独立前后端。现有 Next.js + TypeScript + Tailwind CSS + DeepSeek API 方案是当前阶段成本最低、交付路径最短的选择。

下一步应先确认本评审中的范围和必须修改项，再同步正式文档，之后才开始 Phase 1 编码。
