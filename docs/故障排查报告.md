# Phase 1 首次真实测试故障排查报告

## 1. 结论

本次“本次分析生成失败，请重新尝试。”发生在 **DeepSeek 返回内容的 Zod Schema 校验层**。

DeepSeek 已返回非空内容，返回内容也已经通过 `JSON.parse`。但模型生成的结构化结果中有两个 `evidence` 数组为空，不满足 `analysis-v1` 对证据数组至少包含 1 项的约束，因此服务端抛出 `AI_OUTPUT_INVALID`，最终向前端返回 HTTP 502。

本次只完成根因排查，没有修改应用源码、Prompt、Schema、证据校验或重试策略。

## 2. 已观察到的服务端证据

首次失败请求的服务端终端记录包含：

```text
[deepseek] schema validation failed
roleProfile.riskSignals.1.evidence: too_small
applicationAdvice.reasons.2.evidence: too_small
POST /api/analyze 502
```

日志仅记录校验类型和字段路径，没有记录 API Key、Authorization 请求头、模型原始输出或其他敏感环境变量。

## 4. 直接原因与机制

`src/lib/analysis-schema.ts` 将每个证据数组定义为：

```text
array(string).min(1).max(3)
```

本次模型输出至少包含以下两个空数组：

1. `roleProfile.riskSignals[1].evidence`
2. `applicationAdvice.reasons[2].evidence`

服务端没有放宽校验或把未经验证的模型原文返回前端，这一拦截行为符合当前产品的数据可信度规则。P0 的表现来自模型输出偶发不符合协议，而当前策略又不会对这种 Schema 失败重试或进行受控修复。

## 5. 为什么前端只有通用错误

后端把该问题映射为：

- 内部错误代码：`AI_OUTPUT_INVALID`
- HTTP 状态码：502
- 用户消息：`本次分析生成失败，请重新尝试。`

前端目前只读取并展示 `error.message`，没有保存或展示 `error.code`；API 响应也没有 `request_id`、错误编号或 `retryable` 字段。因此用户无法区分模型格式错误、上游不可用或其他失败类型。

后续错误呈现至少应包含：

- 用户能理解的错误类型；
- 是否建议重试；
- `request_id` 或错误编号；
- 不展示模型原始输出、内部校验路径或堆栈。

## 7. 最小修复实施结果

2026-08-03 已按确认范围完成以下修复：

1. 初始模型结果使用局部容错输入 Schema，只允许 `riskSignals` 和 `applicationAdvice.reasons` 的 evidence 暂时为空；最终 `analysis-v1` Schema 的 `evidence.min(1)` 保持不变。
2. 风险信号没有任何可匹配 JD 原文的 evidence 时删除整条风险，不补造风险，最终 `riskSignals` 允许为空数组。
3. 单条投递理由没有有效 evidence 时删除；只要仍有一条有效理由，整份结果继续进入最终校验。
4. 所有投递理由均无效时，最多调用一次 `jd-analysis-evidence-repair-v1`。修复模型只能按原索引返回“替换 evidence”或“删除”，不能重新生成其他字段。

6. 每次 API 请求生成 `request_id`，错误响应包含 `code`、`message`、`request_id` 和 `retryable`，并通过 `X-Request-ID` 响应头返回编号。

实现未采用自动编造证据、删除 Schema、取消证据校验、`any` 绕过或返回未经验证模型原文的方式。

## 11. ISSUE-002 根因与修复

ISSUE-002 记录为：**模型原始 evidence 数量超过最终 Schema 上限，严格校验早于标准化执行。**

根因是修复 ISSUE-001 时使用的局部输入 Schema 仍对原始 evidence 设置了 `max(3)`。当模型返回 4 条及以上 evidence 时，结果在确定性清理之前触发 Zod `too_big`，因此无法进入有效性过滤、去重和截取流程。

2026-08-03 完成两阶段处理：

1. JSON 解析；
2. Raw AI Output Schema 基础结构校验；
3. evidence 确定性标准化；
4. 无证据非核心条目清理；
5. 必要时执行一次投递理由定向修复；
6. 未放宽的 Final Analysis Schema 校验；
7. 原始 JD 逐字证据校验；
8. 仅将最终可信结果返回前端。

Raw AI Output Schema 允许字符串 evidence 数组为空或超过 3 条，但不能直接返回前端。Final Analysis Schema 继续要求每个保留条目的 evidence 至少 1 条、最多 3 条。

evidence 固定执行：只 trim 首尾 → 删除空值 → 删除无法逐字匹配 JD 的内容 → 删除完全重复项 → 保持原顺序 → 最多保留前 3 条。有效性过滤和去重先于截取。

业务边界保持不变：无证据风险信号和单条投递理由可以删除；核心职责及其他核心画像字段不会被删除或定向修复，清理后 evidence 为空时仍由 Final Analysis Schema 拒绝。

## 14. ISSUE-003 根因与修复

ISSUE-003 记录为：**无候选人资料时，模型将JD任职要求错误归属于用户，并生成虚构个人能力的HR话术。**

根因是原协议只要求 `candidateAdvantages=null` 和 `hrGreeting.personalized=false`，但 `hrGreeting.message` 仍是普通字符串。Prompt 虽要求通用话术，Final Schema 和服务端没有校验话术正文是否把 JD 中的任职要求改写成候选人事实，因此“我具备良好的文档能力和学习能力，日常也关注AI工具的使用”在结构上合法并被返回。

本次仅修复 ISSUE-003：

1. 顶层增加固定状态 `candidateProfileProvided=false`，明确当前只拥有 JD，不拥有用户学历、专业、能力、技能、经历、成果、兴趣或求职状态；
2. `candidateAdvantages` 继续固定为 `null`，不输出个人匹配度或“你的优势”；
3. HR 输出拆分为固定未个性化状态与提示、可直接发送的 `safeGreeting`、保留明确占位符的 `editableGreetingTemplate`；
4. 安全通用版只允许岗位兴趣、JD 职责关注和沟通/确认目的，不允许占位符或候选人事实；
5. 可编辑模板中的个人内容只允许 `【学历/专业】`、`【真实相关技能】`、`【真实项目或实习经历】`；
6. 服务端同时执行结构约束、候选人事实模式检查、安全沟通意图约束和占位符白名单，不依赖简单关键词替换放行；
7. 首次 HR 话术越界时最多调用一次 `jd-analysis-hr-greeting-repair-v1`，只返回 `hrGreeting`，不能重写其他字段；
8. 修复响应结构合法但正文仍越界时，使用固定、无个人事实的安全通用版和占位符模板；修复响应为空、非 JSON 或结构错误时返回 `AI_OUTPUT_INVALID`；
9. 前端分别展示未个性化提示、安全通用版和可编辑模板，并提示占位符必须按真实情况填写。

未修改 ISSUE-004 至 ISSUE-008，未增加个人资料输入、个人档案或其他 Phase 2 功能。

## 17. ISSUE-009：核心职责 evidence 稳定性诊断

### 17.1 已确认失败点

此前 ISSUE-003 首组真实回归的第 3 次请求返回 HTTP 502，失败字段路径为 `coreResponsibilities[1].evidence`。脱敏诊断表明：

- DeepSeek 返回内容非空；
- `JSON.parse` 已通过；
- Raw AI Output Schema 基础结构校验已通过；
- 该 evidence 并非原始空数组，也不是超过 3 条；
- 标准化时共有 2 条 evidence 因无法在案例01原始 JD 中逐字匹配而被删除；
- 删除后 `coreResponsibilities[1].evidence` 为空；
- pending repair Schema 在该路径以 `too_small` 拒绝结果；
- 因此没有进入最终严格 Zod Schema 和最终原文证据校验；
- 最终由 API 返回 502，未向前端返回未经验证的模型内容。

该问题的准确分类是：**核心职责 evidence 无法逐字匹配原始 JD，标准化后为空**，不是 evidence 原始为空、数量超限或 JSON 解析失败。

### 17.2 原始输出保存与复现性

该次只保存了脱敏诊断字段，没有保存未经验证的完整上游模型原始输出；当前不能从日志还原那两条失败 evidence 的原文。这样避免了在常规日志中保留模型原始响应，但也限制了后续对字符差异的离线复盘。

本轮案例01内容复验 3 次均返回 HTTP 200，紧邻此前最终 5 次专项回归也全部成功，因此同一 JD 已连续 8 次未复现该 502。当前结论为偶发、尚不能稳定复现，不能据此视为已经消失。

### 17.3 为什么核心职责不能直接删除降级

`coreResponsibilities` 是 Phase 1 的核心产品输出。直接删除证据失败的职责会产生三类问题：遗漏 JD 的核心工作内容、让用户误以为模型已完整理解岗位、用静默降级掩盖模型证据错误。与可为空的风险信号不同，核心职责承担岗位解析的主干信息，因此必须保持严格完整性，不应采用“删除条目后继续成功”的策略。

### 17.4 处理决定（本轮不实施）

建议后续单独设计最多一次、仅针对 `coreResponsibilities[*].evidence` 的受限定向修复：

1. 只允许替换缺失或无法逐字匹配的 evidence；
2. 只能引用原始 JD 中可逐字匹配的片段；
3. 不得修改职责标题、职责描述、其他职责或其他分析字段；
4. 修复后重新执行 JSON、限定修复 Schema、最终严格 Schema 和原文证据校验；
5. 修复失败继续返回 `AI_OUTPUT_INVALID`，不得删除核心职责或返回 Raw 输出。

本轮按内容验收范围只完成诊断和记录，没有修改实现。完整 3 次输出与评分见 `docs/验收执行报告.md`。

## 19. ISSUE-010：编号列表触发任职要求分类协议冲突

### 19.1 现象与复现

案例02使用329字符原始JD，UTF-8 SHA-256为`f4df62e87e547ff6551470e74f208b9ce835565276c6046cb20c33d05f063ed7`。相同输入连续3次均返回HTTP 502，request_id分别为：

- `86052ea2-4d7c-48a6-a73c-a686f500896a`；
- `76749a4f-bca2-4c09-a4fc-d61c9d0a68f6`；
- `29c195f2-f1d9-47f8-bec5-37db1aa498ab`。

三次均稳定失败于`roleProfile.requirements.0.requirementType`，应用错误码为`AI_OUTPUT_INVALID`。

### 19.2 分层诊断

| 层 | 三次结果 |
|---|---|
| DeepSeek上游 | HTTP调用成功，均只调用1次 |
| 模型内容 | 非空 |
| JSON.parse | 通过 |
| Raw AI Output Schema | 通过 |
| evidence标准化 | 无无效证据、重复或超限删除 |
| 核心职责/投递理由/HR修复 | 均未触发 |
| Final Zod Schema | 失败；路径`roleProfile.requirements.0.requirementType` |
| 原文证据终检 | 未执行 |
| API返回 | 3次均502 |

日志没有保存或输出API Key、Authorization、模型原始内容或敏感响应头。

### 19.3 根因

`normalizeRequirement`用“evidence起始位置的前一个字符”判断是否从未分隔语句中截取。允许的分隔符集合不包含中文JD常见编号`1.`中的半角句点`.`，因此“1.本科及以上……”里的逐字evidence起点被判断为`startsInsideUnseparatedClause=true`，分类优先变为`unclear`。

Final Schema随后独立检查同一evidence中的“本科及以上”或“3年及以上”等硬限制，并要求`requirementType=hard_requirement`。同一条目同时被标准化规则要求为`unclear`、被最终规则要求为`hard_requirement`，形成确定性协议冲突，最终拒绝整份分析。

该问题与岗位领域无关，任何使用`1.`、`2.`编号的硬性任职要求都可能触发；不得通过电气岗位专属硬编码处理。

### 19.4 当前决定

ISSUE-010定级P0。案例02已停止，暂不进行内容评分。当前不修改实现；建议下一轮最小修复仅包含：

1. 将合法列表编号边界与真正的无分隔粘连区分；
2. 统一标准化和Final Schema对“硬限制+范围不清”的优先级；
3. 补充半角/全角列表编号、明确学历和最低年限、真正粘连文本的自动测试；
4. 使用同一案例02原始JD重新连续回归3次。

不得删除Final Schema、放宽硬要求分类、使用岗位硬编码或返回未经验证的模型内容。
