## 1. Phase 1 验收目标

### 1.1 核心目标

验证本地 Demo 能稳定完成以下闭环：

```text
用户输入招聘 JD 文本
        ↓
调用 DeepSeek API
        ↓
返回符合 analysis-v1 的结构化岗位分析
        ↓
网页清晰展示分析结果
```

### 1.2 产品价值目标

确认输出能够帮助应届毕业生和 0–1 年经验求职者：

1. 准确理解岗位主要做什么；
2. 区分硬性要求、核心能力和加分项；
3. 识别工作特点、信息缺口和需要确认的风险；
4. 获得审慎、有限定条件的投递建议；
5. 获得不虚构个人经历的通用 HR 打招呼消息；
6. 看见重要结论所依据的 JD 原文。

### 1.3 工程体验目标

- 有效 JD 能正常提交并得到结果；
- 空、过短和过长输入能被拦截；
- 分析期间有清晰加载状态；
- 请求失败后保留原 JD 并允许重试；
- 桌面和移动端视口均可阅读；
- 页面不显示模型原始错误、密钥或技术堆栈；
- Phase 1 不产生历史记录或持久化数据。

### 1.4 本次验收边界

Phase 1 只接收 JD，不接收个人经历和职业偏好，因此：

- 不验收真正的人岗匹配准确率；
- 不验收匹配百分比；
- 不要求系统判断某位具体用户一定适合或不适合岗位；
- `candidateAdvantages` 应为 `null`，页面不应展示优势分析；
- “投递建议”只评价 JD 的信息完整度和岗位条件；
- HR 话术只能是非个性化通用版本。

本文件中的“匹配分析可信度”用于评价系统是否守住上述边界，而不是评价尚未实现的个人匹配功能。

## 2. 测试岗位类型

本轮使用 10 类案例覆盖常见岗位和边界情况。详细模板见 [测试案例.md](测试案例.md)。

| 案例 | 类型 | 主要验证点 |
|---|---|---|
| TC-01 | 高匹配岗位 | 不因人工参考候选人看似匹配而生成个人优势 |
| TC-02 | 跨岗位 | 能识别岗位能力，但不擅自判断候选人可迁移能力 |
| TC-03 | 低匹配岗位 | 不输出个人不匹配结论或录用概率 |
| TC-04 | 信息不足 JD | 少推断、多暴露信息缺口和确认问题 |
| TC-05 | AI 相关岗位 | 正确解释 AI 术语和业务职责，不夸大岗位技术性 |
| TC-06 | 技术岗位 | 区分必备技术、加分技术和具体工作职责 |
| TC-07 | 产品岗位 | 区分产品职责、协作特点和隐含能力要求 |
| TC-08 | 销售岗位 | 识别业绩、客户开发和薪酬确认点，避免负面定性 |
| TC-09 | 运营岗位 | 正确拆分内容、活动、用户和数据职责 |
| TC-10 | 隐含风险岗位 | 审慎识别模糊职责、压力和薪资风险，不断言欺诈 |

### 2.1 人工参考候选人说明

TC-01、TC-02 和 TC-03 可设置一个“人工参考候选人”，仅供验收人员判断系统是否越界。参考候选人信息不得输入 Phase 1 产品，也不作为 DeepSeek Prompt 内容。

预期行为：无论人工判断为高匹配、跨岗位还是低匹配，系统都只能基于 JD 生成岗位分析，不得声称用户具备或缺少某项能力。

## 4. 人工评价标准

### 4.1 通用评分

所有维度使用 1–5 分：

| 分数 | 定义 |
|---:|---|
| 5 | 准确、具体、可直接使用，无明显问题 |
| 4 | 整体正确，有轻微遗漏或措辞问题 |
| 3 | 基本可用，但存在明显改进空间 |
| 2 | 多处错误或容易误导，需要较大修改 |
| 1 | 严重错误、越界或不可用 |

### 4.2 JD 理解准确性

重点判断：

- 岗位名称、地点、薪资、经验和学历是否忠于原文；
- 核心职责是否完整且没有混入任职要求；
- 硬性条件与“优先、加分、有则更佳”是否正确区分；
- AI 推断是否标记为 `inferred`；
- 未知信息是否保持未知。

评分参考：

- 5：关键信息与人工标注一致，无关键误分类；
- 4：存在一项轻微遗漏，不影响总体理解；
- 3：有 1–2 项明显遗漏或次要误分类；
- 2：核心职责或硬性要求多处错误；
- 1：岗位理解方向错误或大量编造。

### 4.3 岗位真实画像价值

重点判断：

- 是否把零散 JD 转化为新手能理解的工作画像；
- 核心能力和工作特点是否有实际信息增量；
- 风险信号是否具体、审慎且有证据；
- 信息缺口和 HR 确认问题是否真正影响求职决策；
- 是否避免堆砌通用空话。

评分参考：

- 5：画像清晰、具体，能明显改善用户判断；
- 4：大部分有价值，少量内容泛化；
- 3：可用但较表面，信息增量有限；
- 2：大量套话或风险解读不合理；
- 1：画像误导或与 JD 明显冲突。

### 4.4 投递建议合理性

重点判断：

- 建议是否只基于 JD 信息与岗位条件；
- 建议等级是否与风险和信息完整度一致；
- 理由是否可追溯；
- 是否包含“不代表人岗匹配”的限制；
- 是否避免绝对化投递结论。

评分参考：

- 5：等级、理由和限制完整一致；
- 4：方向合理，理由可再具体；
- 3：建议基本合理但过于泛化；
- 2：建议与已识别风险或信息缺口矛盾；
- 1：输出绝对结论、录用概率或明显误导建议。

### 4.5 匹配分析可信度

Phase 1 评分的是边界可信度：

- 是否明确当前没有个人经历输入；
- `candidateAdvantages` 是否保持 `null` 且页面不展示；
- 是否避免声称用户具备或缺少某项技能；
- 是否避免输出匹配分数、录用概率或个人适配结论；
- 投递建议是否没有伪装成人岗匹配结果。

评分参考：

- 5：边界清晰，没有任何候选人事实断言；
- 4：限制说明略弱，但没有越界结论；
- 3：措辞容易让人误解为匹配建议，但未编造事实；
- 2：暗示用户具备优势或适合岗位；
- 1：编造用户经历、输出匹配分或明确个人适配结论。

### 4.6 HR 话术自然程度

重点判断：

- 是否像真实招聘平台初次沟通；
- 是否简洁、礼貌且目的清楚；
- 是否引用岗位具体职责，而不是完全通用模板；
- 是否避免过度客套、机械或冗长；
- 是否没有虚构个人优势；
- 是否提醒发送前补充真实经历。

评分参考：

- 5：自然具体，少量修改即可使用；
- 4：整体自然，存在轻微模板感；
- 3：可用但明显泛化或略显生硬；
- 2：冗长、机械或含未经支持的个人断言；
- 1：严重虚构、冒犯或无法使用。

### 4.7 是否存在 AI 幻觉

该维度分数越高越好：

- 5：没有发现幻觉，事实和证据均来自 JD；
- 4：存在一项较弱推断，但已正确标记且有依据；
- 3：存在可疑推断或证据引用不够准确；
- 2：编造一项重要岗位事实或引用不存在的原文；
- 1：多项事实编造，或编造用户经历、公司信息、薪资福利。

以下情况直接记为重大幻觉：

- 引用的证据在 JD 中不存在；
- 把未写明的薪资、地点、学历或经验当作事实；
- 把加分项写成硬性要求；
- 声称用户拥有未输入的经历、能力或成果；
- 断言公司违法、欺诈或一定存在问题。

## 6. 需要重点观察的问题

### 6.1 岗位事实与分类

- 是否把职责、要求、福利混在一起；
- 是否把“优先、加分、有则更佳”误判为硬门槛；
- 是否丢失年限、学历、到岗天数、证书等限定词；
- 是否将岗位常识误写成 JD 明示事实；
- 相同内容重复出现时是否造成结果重复。

### 6.2 岗位真实画像

- 推断是否有足够原文依据；
- 风险信号是否被夸大；
- 是否把“抗压、服从、接受加班”等词直接等同于企业有问题；
- 信息不足时是否主动降低结论强度；
- 待确认问题是否具体，是否能直接向 HR 提问。

### 6.3 投递建议

- 信息完整但要求较高的岗位，是否被误判为“不值得投”；
- 信息不足的 JD，是否错误输出积极结论；
- 风险较多的岗位，建议是否仍然过于乐观；
- 是否出现“你适合”“你不匹配”等越界说法；
- `limitations` 是否持续说明建议不含个人经历和外部公司信息。

### 6.4 HR 话术

- 是否出现不存在的“我的项目”“我的经验”“我擅长”；
- 是否只替换岗位名称，缺少岗位相关性；
- 是否超过正常招聘平台首次沟通长度；
- 岗位名称缺失时是否使用自然的中性表达；
- 是否提示用户补充真实经历后再发送。

### 6.5 AI 幻觉和证据

- 引用是否能逐字或仅忽略空白后在 JD 找到；
- AI 推断是否被错误标记为 `explicit`；
- 未写明字段是否正确返回 `null`；
- 是否生成公司规模、团队氛围、晋升空间等外部事实；
- 是否因岗位名称推断 JD 未写明的日常工作。

### 6.6 稳定性与体验

- 同一 JD 重复运行时，核心结论是否大体一致；
- 加载时间是否在用户可接受范围；
- 服务失败时是否保留原输入并可恢复；
- 长内容在移动端是否易读；
- 空数组是否产生无意义或破损卡片；
- 优势分析模块是否始终隐藏。

## 7. 总体验收门槛

建议采用以下门槛：

### 7.1 通过

Phase 1 十案例验收标准（2026-08-07 冻结，统一取代旧“每维≥3.5”口径）：

**单案例通过条件（适用于 TC-01～TC-10 各自判定）：**

- 真实请求链路必须成功：当前案例使用同一原始 JD 连续执行 3 次，3/3 HTTP 200；
- Final Schema 必须通过；
- 原文 evidence 校验必须通过；
- 候选人事实幻觉必须为 0；
- 当前案例不得存在由该案例新发现或直接触发的未关闭 P0 / P1；其他已经隔离、明确不属于当前案例测试目标的已知 P1，不阻塞该案例的执行和判定；
- 八维综合平均分必须 >= 3.8（八维口径：核心职责提炼准确性、任职要求分类准确性、岗位真实画像价值、风险信号合理性、投递建议边界与行动价值、HR 安全通用话术自然程度、可编辑模板实用性、结论与原文证据一致性）；
- 任一单项不得低于 3.0；
- 单项为 3.0 时允许案例通过，但必须记录对应的 P2 或一般优化问题，不得忽略；
- 如果存在确定性的协议错误，即使综合分达到门槛，也不得通过；
- P2 与一般优化项可以进入问题池，不阻塞当前案例，但必须记录；
- 没有编造用户经历或个人匹配结论；
- 优势分析模块在全部案例中均未展示；
- 核心流程、失败恢复和移动端阅读无阻断问题。

**Phase 1 总验收条件（适用于 Phase 1 正式结束）：**

- 10 个案例全部执行；
- Phase 1 正式结束前不得存在未经明确决策的未关闭 P0 / P1；未关闭 P0 不得存在，P1 必须修复关闭，或经过产品决策重新定级 / 接受风险后关闭；
- ISSUE-012 当前属于独立 robustness P1：不阻塞标准 TC-03～TC-10 的单案例执行与判定，但在 Phase 1 总验收前必须重新决策；不得因“不阻塞单案例”而自动降低其优先级。

### 7.2 有条件通过

- 没有 P0 问题和用户经历编造；
- 核心流程可用；
- 存在少量 P1/P2 质量问题，但问题明确、可复现且不需要扩大 Phase 1 范围；
- 修复后需针对失败案例重新验收。

### 7.3 不通过

出现任一情况：

- 核心流程在 10 个案例中失败 2 次以上；
- 出现密钥或敏感信息泄露；
- 编造用户经历或输出个人匹配结论；
- 多次编造关键岗位事实或引用不存在的证据；
- 投递建议存在明显误导；
- 主要结果卡片无法正常展示。
