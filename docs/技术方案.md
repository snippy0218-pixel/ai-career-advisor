# AI 求职顾问 Phase 1 技术方案

> 版本：V1.0  
> 适用范围：Phase 1 本地 Demo  
> 更新日期：2026-08-03

## 1. 技术目标

用最小架构完成以下链路：

```text
浏览器输入 JD
  → Next.js 服务端接口
  → DeepSeek API
  → JSON 解析与校验
  → 浏览器展示结构化分析
```

Phase 1 是一个 Next.js 单体应用，不拆分独立前后端服务。

## 2. 技术栈

- Next.js（App Router）；
- TypeScript；
- Tailwind CSS；
- DeepSeek API。

允许使用 Zod 作为轻量运行时数据校验工具。Zod Schema 是运行时校验来源，TypeScript 类型从 Schema 推导或保持与其一致，不重复维护两套结构。

## 3. 系统边界

### 3.1 Phase 1 使用

- React 页面和组件；
- 浏览器本地组件状态；
- Next.js Route Handler；
- 服务端环境变量；
- 原生 `fetch` 调用 DeepSeek；
- JSON Output；
- 轻量单元测试和接口模拟测试。

### 3.2 Phase 1 不使用

- PostgreSQL；
- Redis；
- 对象存储；
- 消息队列；
- 独立后端；
- 数据库 ORM；
- 用户认证与权限；
- SSE、WebSocket 或流式任务系统；
- 全局状态管理库；
- 多模型路由。

### 4.1 前端职责

- 保存 JD 文本和本次分析结果；
- 管理 `idle`、`loading`、`success`、`error` 四种状态；
- 提交 `/api/analyze`；
- 展示用户可理解的错误信息；
- 按 [analysis-schema.md](analysis-schema.md) 展示结果；
- `candidateAdvantages` 为 `null` 时不展示该模块。
- 展示未个性化提示、安全通用话术和保留明确占位符的可编辑模板。

Phase 1 使用 React 本地状态即可，不引入 Redux、Zustand 或服务端持久化状态。

### 4.2 服务端职责

- 校验请求体；
- 读取 DeepSeek 服务端环境变量；
- 组装 Phase 1 Prompt；
- 调用 DeepSeek；
- 处理超时、重试和上游错误；
- 解析 JSON；
- 执行运行时 Schema 和证据校验；
- 在 `candidateProfileProvided=false` 时校验 HR 话术的候选人事实边界，必要时只修复 `hrGreeting` 一次；
- 确定性校正任职要求分类、事实/推断来源与成长性表达；
- 核心职责 evidence 清理后为空时，必要时只修复失败职责的 evidence 一次；
- 返回统一 API 响应。

### 4.3 单一数据契约

[analysis-schema.md](analysis-schema.md) 是唯一业务输出协议。

实现规则：

- DeepSeek 必须以该结构为输出目标；
- Route Handler 只返回通过该结构校验的数据；
- TypeScript 类型以该结构为参考；
- 前端不得自己重命名或推测字段；
- 变更协议时同步更新 Prompt、Schema、前端和测试。

## 5. API 设计

### 5.1 `POST /api/analyze`

请求：

```json
{
  "jdText": "完整的招聘JD文本"
}
```

请求限制：

- `jdText` 必须为字符串；
- 去除首尾空白后为 100–12,000 个字符；
- 不接收文件、URL 或个人经历字段。

成功响应：

```json
{
  "data": {
    "schemaVersion": "analysis-v1",
    "candidateProfileProvided": false,
    "basicInfo": {},
    "coreResponsibilities": [],
    "roleProfile": {},
    "applicationAdvice": {},
    "candidateAdvantages": null,
    "hrGreeting": {}
  },
  "error": null
}
```

错误响应：

```json
{
  "data": null,
  "error": {
    "code": "AI_SERVICE_UNAVAILABLE",
    "message": "分析服务暂时不可用，请稍后重试。",
    "request_id": "服务端生成的请求编号",
    "retryable": true
  }
}
```

每次请求均生成 `request_id`，同时写入响应头 `X-Request-ID`。错误响应只返回安全错误类型、用户文案、请求编号和是否建议用户重试，不返回模型原文、堆栈或上游鉴权信息。

## 6. DeepSeek 调用策略

### 6.1 接口与配置

- 使用 DeepSeek 官方 OpenAI 兼容的 Chat Completions API；
- Base URL 默认使用 `https://api.deepseek.com`，集中配置；
- 调用路径为 `/chat/completions`；
- API Key 使用服务端环境变量 `DEEPSEEK_API_KEY`；
- 模型使用环境变量 `DEEPSEEK_MODEL` 配置；
- Phase 1 默认选择当前可用的 Flash 模型，开发当天再次核对官方模型名；
- 不使用任何 `NEXT_PUBLIC_` 形式保存 DeepSeek 密钥。

### 6.2 生成参数

- 非思考模式，明确设置 `thinking.type = "disabled"`；
- `stream: false`；
- JSON Output：`response_format` 使用 `json_object`；
- Prompt 明确包含“JSON”字样和完整结构示例；
- 温度建议 `0.2`，优先稳定分类；
- `max_tokens` 初始设置为 `3000`，若真实样例频繁截断再调整；
- 只有正常结束的响应才进入 JSON 解析；
- `finish_reason = length`、内容安全终止或资源不足均作为异常处理。

不使用 SSE 或流式响应，因为完整 JSON 必须在返回前统一校验。

### 6.3 超时

- `/api/analyze` 应用级总超时：60 秒；
- 超时覆盖初次请求和可能的一次重试；
- 达到总超时后中止上游请求；
- 页面提示“分析时间过长，请重新尝试”，并保留 JD。

### 6.4 重试策略

初始分析最多进行一次上游故障自动重试。证据定向修复和 HR 话术定向修复不属于上游故障重试，均各自最多执行一次，并共同服从 60 秒总超时。

允许自动重试：

- HTTP 429；
- HTTP 500；
- HTTP 503；
- 响应内容为空；
- 响应缺少有效选择项。

不自动重试：

- HTTP 400；
- HTTP 401；
- HTTP 402；
- HTTP 422；
- 请求超时；
- JSON 可以解析但业务 Schema 不通过；
- 内容安全终止。

重试必须服从 60 秒总超时，不引入任务队列。

证据定向修复不属于上游故障重试。初次结果中：

- `roleProfile.riskSignals` 的无效条目直接删除，不补造风险；
- `applicationAdvice.reasons` 的无效条目直接删除；
- 删除后仍有有效投递理由时直接进入最终校验；
- 所有投递理由均无效时，最多额外调用一次证据定向修复；
- 定向修复只返回按原索引“替换 evidence”或“删除条目”的操作，不能修改其他分析字段；
- 定向修复失败后返回 `AI_OUTPUT_INVALID`。

HR 话术事实边界修复同样不属于上游故障重试：

- Phase 1 顶层固定 `candidateProfileProvided=false`，系统只有 JD，没有用户学历、专业、能力、技能、经历、成果、兴趣或求职状态；
- 最终结果必须同时包含固定未个性化提示、可直接发送的 `safeGreeting` 和使用批准占位符的 `editableGreetingTemplate`；
- 服务端不把 JD 任职要求视为候选人事实，同时使用结构约束、候选人事实模式、受限沟通意图和占位符白名单校验；
- 首次话术越界时最多额外调用一次 `jd-analysis-hr-greeting-repair-v1`，输入只包含 JD 和原 `hrGreeting`，输出不能覆盖其他分析字段；
- 修复响应结构合法但正文仍越界时，替换为固定无个人事实安全通用版和固定占位符模板；
- 修复响应为空、非 JSON 或结构错误时返回 `AI_OUTPUT_INVALID`，不返回首次或修复模型的原始话术。

### 6.5 输出校验

依次执行：

1. 上游 HTTP 状态检查；
2. `finish_reason` 检查；
3. 模型内容非空检查；
4. JSON 解析；
5. 使用 Raw AI Output Schema 校验字段类型和基础结构；Raw evidence 只要求为字符串数组，允许为空或超过 3 条；
6. 对每个 evidence 数组依次执行首尾 trim、空值删除、JD 逐字匹配、完全去重、保序和最多保留前 3 条；有效性校验必须早于截取；
7. 删除清理后没有证据的风险信号和投递理由；记录 evidence 为空的核心职责作为独立修复候选；
8. 如存在核心职责候选，最多执行一次仅针对这些职责 evidence 的定向修复；只允许补充逐字证据或删除无法证明的职责，删除后数量低于 Final Schema 最低值则失败；
9. 所有投递理由均失效时，必要时执行一次投递理由证据定向修复；
10. 确定性归类 `requirementType`，校正 `sourceType`，为 `to_verify` 补齐对应 HR 问题，并收敛无依据的确定性成长表达；
11. 确认 `candidateProfileProvided === false` 和 `candidateAdvantages === null`；
12. 校验 HR 未个性化状态、固定提示、安全通用版候选人事实边界和可编辑模板占位符；
13. HR 边界失败时最多执行一次只覆盖 `hrGreeting` 的定向修复；
14. 使用未放宽的 Final Analysis Schema 校验数量、长度、枚举、分类语义、`sourceType`、evidence `min(1)/max(3)` 及 HR 事实边界；
15. 执行 JD 原文证据字符串包含校验。

任何一步失败都不得把模型原始内容直接返回页面。

Raw AI Output Schema 只用于不可信模型 JSON 的进入和标准化，不能作为 API 成功响应。Final Analysis Schema 仍是前端可展示结果的唯一协议，最终 `evidence.max(3)` 没有取消或放宽。

## 7. 错误处理

| 上游或内部问题 | 内部错误码 | 用户提示 | 是否重试 |
|---|---|---|---|
| 请求校验失败 | `INVALID_INPUT` | 请粘贴完整且长度合适的招聘信息 | 否 |
| 401 | `AI_AUTH_FAILED` | 分析服务配置异常 | 否 |
| 402 | `AI_BALANCE_INSUFFICIENT` | 分析服务暂时不可用 | 否 |
| 429 | `AI_RATE_LIMITED` | 当前使用人数较多，请稍后重试 | 一次 |
| 400/422 | `AI_REQUEST_INVALID` | 分析服务配置异常 | 否 |
| 500/503 | `AI_SERVICE_UNAVAILABLE` | 分析服务暂时不可用，请稍后重试 | 一次 |
| 超时 | `AI_TIMEOUT` | 分析时间过长，请重新尝试 | 否 |
| 空内容/无选择项 | `AI_EMPTY_RESPONSE` | 本次分析生成失败，请重新尝试 | 一次 |
| JSON、最终 Schema 或定向修复错误 | `AI_OUTPUT_INVALID` | 本次分析生成失败，请重新尝试 | 不自动重试；允许用户重试 |
| 内容安全终止 | `AI_CONTENT_BLOCKED` | 当前内容无法完成分析 | 否 |

前端显示用户可理解的错误类型、重试建议和 `request_id`，不显示上游响应体、模型原文、内部校验路径、堆栈或 API 配置。

## 8. 本地状态与数据

- JD、加载状态、错误和分析结果保存在当前 React 组件状态；
- 页面刷新后数据可以丢失；
- 不使用浏览器长期存储作为正式功能；
- 不写入服务器文件；
- 不使用数据库；
- 服务端日志不记录完整 JD，只记录错误类型和耗时等最小诊断信息。

## 9. 安全要求

- `.env.local` 不提交版本库；
- 提供不含真实密钥的 `.env.example`；
- 浏览器不直接访问 DeepSeek；
- JD 使用明确边界标签包裹并视为不可信文本；
- 不渲染模型返回的原始 HTML；
- 限制请求体大小；
- Prompt 要求忽略 JD 中的指令；
- 不在日志中保存完整 JD 和敏感信息。

## 10. 测试与完成定义

轻量测试范围：

- 请求输入校验；
- `analysis-v1` Schema 校验；
- 证据包含校验；
- DeepSeek 成功、空内容、无效 JSON、429、500 和超时模拟；
- 页面加载、成功、错误和重试状态；
- 至少 5–10 条脱敏 JD 人工回归；
- 加分项不被归类为硬性要求；
- 提示注入文本不能改变任务和输出协议；
- JD 任职要求不能被改写为候选人已具备的能力、学历、专业、经历或兴趣；
- 无个人资料时安全通用话术可直接发送，模板个人信息全部保留为批准占位符；
- HR 初稿越界后的定向修复成功、固定安全兜底和结构性修复失败均有自动测试。

Phase 1 完成条件：lint、测试和生产构建通过，本地可重复完成真实 API 演示。

## 11. 暂不引入的技术

Phase 1 不为后续需求提前建设基础设施。PostgreSQL、Redis、对象存储、消息队列、OCR、SSE、用户认证、权限系统和复杂评测平台均不在当前技术方案中。

## 12. 第二轮内容协议与 ISSUE-009

当前主 Prompt 为 `jd-analysis-v1.2`。岗位画像协议统一为：

- `sourceType = jd_explicit | inference | to_verify`；
- `requirementType = hard_requirement | core_requirement | preferred_requirement | unclear`；
- `roleProfile.requirements` 是唯一任职要求数组。

服务端先执行 Raw Schema 与 evidence 标准化，再按 JD 限定词确定性校正任职要求；综合岗位画像使用审慎推断，无法确定的参与深度、培养机制等转为 `to_verify` 并优先加入 `questionsToConfirm`。Final Schema 同时校验分类依据、推断措辞、待确认问题联动和无依据成长断言。

ISSUE-009 使用 `jd-analysis-core-evidence-repair-v1`：只接收 evidence 失效的核心职责索引、标题、正文和来源类型；最多调用一次；只能补充逐字 evidence 或删除无法证明的职责；不能重写整份分析。修复后先经过限定修复 Schema，再进入投递理由、HR 和最终严格校验。核心职责剩余数量低于最低要求时返回 `AI_OUTPUT_INVALID`。

工程结果：4 个测试文件、50 项全部通过，lint 与 production build 通过。案例01正式复验 3/3 HTTP 200、Final Schema 和原文证据校验 3/3 通过、502 为 0。

## 13. Phase 3.1 — 本地候选人档案存储决策

> 更新日期：2026-08-16；状态：COMPLETE / CLOSED（实现提交 `b39c041` → `a9e071a`）

### 13.1 决策

1. 使用浏览器 `localStorage` 做第一版本地持久化，key 为 `ai-career-advisor:candidate-profile:v1`；不引入数据库、服务端存储或状态库。
2. 只持久化原始资料文本：`{ schemaVersion, updatedAt, rawText, rawTextSha256 }`（Zod strict schema）。**不持久化** `candidate-profile-v2` 结构化结果，保持「raw profile text 是唯一 truth source」不变。
3. `rawTextSha256` 使用仓库内自包含 SHA-256 实现（FIPS 180-4，无新依赖），用于加载时完整性校验。
4. 加载时：JSON 损坏 / 版本不符 / sha 不匹配 → 返回 `invalid`，**不覆盖**原 key（非破坏性），UI 降级为手动输入。
5. 仅在客户端 `useEffect` / 事件中读写（SSR 守卫），避免 hydration mismatch。
6. `/personalized-match` 采用**预填**方式加载档案：挂载时读取并填入资料文本框，用户手动提交；不自动触发任何模型调用。
7. 新增 `profile-completeness.ts` 轻量前端提示（教育背景 / 技能 / 项目 / 工作与实习经历 / 求职目标）：关键词检测，仅建议，不阻塞、无评分。

### 13.2 边界

- 不改 `candidate-profile-v2`、`/api/profile/analyze`、match / recommendation / strength-gap / greeting 契约；
- 不写服务器文件；隐私提示与清除入口随页面提供；
- 跨标签页同步、导入导出、登录与云端同步留待后续版本。
